# FutureProof — 2-Minute Demo Script

This script is optimized for a live hackathon judging slot. It keeps the technical claim narrow and evidence-backed:

> Both implementations pass today's tests. FutureProof measures which one creates more observed friction under the same plausible future changes.

## Before the demo

Have these ready:

- the FutureProof report dashboard,
- the `FR-04` evidence drawer,
- the server-generated JSON export endpoint,
- the repository README/methodology if a judge asks how scoring works.

If live model credentials are configured and the environment is stable, run the live analysis.

If a live model is unavailable, **do not pretend the mocked browser visual is a new live run**. Use the deterministic golden run / precomputed controlled demo evidence and say so explicitly:

> “For judging reliability I’m showing the precomputed controlled demo report. The repository also contains a credential-gated real-model smoke workflow; deterministic CI does not depend on paid model calls.”

## 0:00–0:15 — The problem

**Say:**

“Code review tells us whether a pull request works today. It usually cannot tell us which of two correct implementations will be easier to evolve six months from now.”

“Here I have two implementations of the same shipment-notification change. Candidate A and Candidate B both start with **22 out of 22 tests passing**.”

**Show:**

- Candidate A current-test proof.
- Candidate B current-test proof.

**Key point:** current correctness is intentionally tied.

## 0:15–0:35 — The experiment

**Say:**

“FutureProof freezes five plausible future requirements before either candidate is tested: SMS notifications, user preferences, retries, provider fallback, and push notifications.”

“Both candidates get the **same model, same tool surface, same budget, and the same scenario order**. Each candidate-scenario trial runs in a fresh sandbox.”

“The hard provider-fallback scenario is repeated three times per candidate, so the full demo contains **14 isolated candidate executions**.”

**Show:**

- The five future scenarios.
- If running live, click **Start Analysis** and briefly show the SSE-driven progress state.

## 0:35–0:58 — What FutureProof measures

**Say:**

“The coding agent is not the judge. The agent only tries to implement the future requirement.”

“FutureProof deterministically measures whether the future acceptance tests pass, how many tool calls and files were needed, how much regression pressure appeared after edits, token use, and structural deltas.”

“An important detail: the agent does not receive the hidden regression score, so it cannot directly optimize for that benchmark number.”

**Show:**

- Measured Evidence row.
- Tasks Passed.
- Tool Calls.
- Files Touched.
- Regression Cycles.
- Token Usage.
- Structural Delta.

## 0:58–1:20 — The comparison result

If you are showing the approved deterministic demo report, **say**:

“In this controlled demo report, Candidate A lands at **18 Future Risk** while Candidate B lands at **74**.”

“Those numbers are not AI opinions. They come from four deterministic dimensions: resilience, efficiency, regression pressure, and structural change.”

“Missing evidence is never treated as zero risk; the available weights are renormalized.”

**Show:**

- 18 / 100 on Candidate A.
- 74 / 100 on Candidate B.
- Radar comparison.
- Scenario Results Overview.

**Do not say:** “Candidate A is universally 4× more maintainable.”

**Safer claim:**

“Under these frozen future requirements, this agent, this budget, and these acceptance tests, Candidate B showed substantially more observed change friction.”

## 1:20–1:43 — Open the evidence

Open **FR-04 — Add provider fallback**.

**Say:**

“This is the hardest composition scenario. It is repeated three times to reduce single-run model variance.”

“The drawer shows the frozen requirement and provenance, acceptance evidence, A/B metrics, regression snapshots, remaining failures, and the raw patch/tool-event artifacts.”

“The browser never receives server filesystem paths. It can only request evidence through the analysis ID, scenario ID, candidate ID, trial number, and an allowlisted artifact type.”

**Show:**

- Frozen requirement/provenance.
- A vs. B metrics.
- Regression evidence.
- Candidate B remaining failure.
- Patch or tool events if time permits.

## 1:43–1:55 — Reproducibility

Click **Export**.

**Say:**

“The export is generated by the server, not rebuilt independently in the browser. FutureProof writes `report.json`, a human-readable `report.md`, and a manifest containing SHA-256 checksums.”

“So a judging result has a reproducible evidence bundle, not just a screenshot.”

## 1:55–2:05 — Close

**Say:**

“FutureProof does not try to predict the one true future or assign a universal maintainability score.”

“It gives code review a controlled stress test for a question we normally answer by intuition: **when both implementations work today, which one is more resilient to tomorrow's changes?**”

# Judge Q&A

## “Isn't this just AI grading AI?”

No. The LLM may generate scenarios and act as the coding agent, but it does not assign the final score.

FutureProof calculates scores from deterministic evidence: scenario status, tool calls, files touched, edits, test cycles, token use, regression snapshots, and structural deltas. If an LLM is used to explain a result, unsupported numeric claims are rejected and the system falls back to deterministic evidence-only prose.

## “How do you stop the future scenarios from favoring one PR?”

Scenario generation is blind to Candidate A/B implementation context. The accepted scenarios are frozen before candidate execution and validated for neutrality, behavioral acceptance criteria, external-dependency constraints, duplication, and the required difficulty mix.

Both candidates then receive the exact same scenario set and scenario order.

## “How do you handle model randomness?”

The hard scenario is repeated three times per candidate. Scalar evidence is aggregated with medians; status uses majority vote, with ties broken toward the more severe outcome. All raw trials remain in the artifacts.

The deterministic CI golden test does not call an external model, so repository verification itself is reproducible.

## “Couldn't the agent game the score?”

The agent does not receive the final score or the hidden regression-pressure score. Its tools are constrained, commands are allowlisted, and regression probes are observer-side evidence after edits.

No benchmark is impossible to game, but FutureProof separates the actor from deterministic measurement and avoids directly exposing the target metrics to the actor.

## “Why use tool calls/files touched? Fewer isn't always better.”

Correct. No single metric is treated as maintainability.

FutureProof combines several signals: behavioral resilience, implementation effort, regression pressure, and structural change. The result should be interpreted comparatively for the specified experiment, not as an absolute quality score.

## “Why is provider fallback repeated but the others aren't?”

It is the deliberately hard composition scenario and is expected to have the highest run variance. Repeating it gives the demo variance reduction where it matters most without multiplying every hackathon run's time/token cost.

The trial policy is explicit and persisted, so a production benchmark could repeat more scenarios if budget allows.

## “What happens when evidence is missing?”

FutureProof represents missing regression or structural evidence as `null`, not zero. Overall-risk weights are renormalized across the evidence dimensions that are actually available.

## “Can I inspect the exact evidence behind a score?”

Yes. Every candidate/scenario/trial persists metadata, tool events, test results, patch, metrics, and summary artifacts. The UI evidence drawer accesses raw evidence through safe opaque routes.

The public report and exports strip server-only artifact paths.

## “Does the real demo require OpenAI?”

The engine uses an OpenAI-compatible model adapter. The live API can point at a compatible endpoint using `LLM_BASE_URL`, `LLM_API_KEY`, and `LLM_MODEL`.

Normal CI deliberately does not require a paid model call. A separate credential-gated manual workflow validates the real compatible JSON-completion path when credentials are available.

## “Did you actually run that real-model workflow?”

Use the answer that is true at judging time.

If it has run successfully:

> “Yes. The manual real-model smoke passed against [model/endpoint]. The deterministic benchmark tests remain separate so CI is reproducible.”

If it has not been run:

> “The credential-gated workflow and adapter contract are implemented and tested, but I am not presenting an unverified live-model run as evidence. The report shown here comes from the deterministic controlled demo/golden path.”

## “Is 18 vs. 74 a universal property of these architectures?”

No.

It is the result for this frozen future set, acceptance contracts, scoring model, agent configuration, and budget. The valuable claim is comparative and experimental: one candidate showed materially more observed change friction under the same controlled futures.

## “What would you build next?”

The MVP deliberately owns a small TypeScript/npm fixture for strong experimental control. The next steps are repository/PR ingestion, more languages/build systems, hardened container/VM isolation, wider repeated-trial support, and domain-specific scenario/acceptance generation.
